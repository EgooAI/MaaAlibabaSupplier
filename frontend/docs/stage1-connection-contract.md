# Connection Integration (Stages 1 and 2)

The frontend uses the existing API envelope: `{ code: 0, msg: string, data: ConnectionSnapshot }`. All four connection endpoints return that envelope. A non-zero code or non-2xx status is an error. No backend files are changed by this implementation.

- `GET /api/settings/connection` only observes. Initial load, focus, visibility, visible 10-second polling, and cross-tab notifications call this endpoint.
- `POST /api/settings/connection/connect` sends `{ epoch }`. Initialization must not click the client. Each successful connection clears prior manual confirmation.
- `POST /api/settings/connection/confirm` sends `{ epoch, window_generation }`, captured when the user opens the explicit seller confirmation dialog.
- `POST /api/settings/connection/retry` sends `{ epoch }`. Initial key verification and recovery from an unverified/invalid/unavailable key require this explicit action. Once verified, the backend worker checks and synchronizes the source independently of frontend polling. The response acknowledges submission, not completion.

`epoch` is an opaque string token. `source.revision` is the durable, atomically committed CRM view revision and drives list/detail refresh. `source_revision` and `applied_source_revision` describe source progress without triggering reloads. `last_checked`, `last_attempt`, `last_success`, and nullable `retry_at` use Unix seconds. `counts` contains `inserted`, `updated`, and `unchanged`; `pending`, `syncing`, `auto_enabled`, and `source_dirty` describe worker state. `freshness` is exactly `fresh | syncing | stale`. `account.data_dir` must be the canonical directory for durable draft identity; `data_dir.path` must be the resolved directory so that valid-to-valid changes remount account selection. The snapshot carries no server-side `steps` or `model.verified`: the settings page derives its step indicator client-side from `data_dir.state`, `account.self_ali_id`, `source.key_validation`, `source.ready/last_error/phase`, `client.connected/confirmed`, and `model.configured`, so those fields remain the single authority. Internal sync diagnostics (`source_mtime`, `cache_time`, `wal_frames_applied`, `last_refresh_ms`, `wal_pipeline`) are excluded from the connection and conversation-revision payloads; the status page still receives them via `/api/status`.

Requests under `/api/conversations`, `/api/messages`, `/api/self-info`, and the account-scoped write `/api/cache/reset` send `X-Account-Epoch`. The client captures the token before fetch, rejects results if the local account lifetime changes, and rejects a present response `X-Account-Epoch` if it differs from the captured token. Missing response headers remain accepted. Chat and batch requests also bind to their mounted workspace, preventing an old async continuation from acquiring the next account's token. Backend `account_scope.py` also scopes `/api/sync-state`; the frontend currently has no caller for that endpoint.

The frontend sends the epoch and requires only `client.connected` for `/api/status/node-test`. This read-only diagnostic still sends `{ entry }`; the backend captures `window_generation` when enqueueing and rechecks the epoch and window before execution. Manual confirmation is not required for diagnostics. Send, input-test and goto-contact continue to require `operate_client` and are independently guarded by the backend. Cache reset requires the epoch but not a connected or confirmed client. Account data writes without the expected epoch are rejected server-side.

Directory, Ali ID, and key writes use the existing settings endpoints. `mutate` captures the authoritative epoch before invalidating existing account work, then passes that captured token to its operation callback. `PUT /api/settings/alibaba-data-dir`, `PUT /api/settings/ali-id`, `PUT /api/settings/ali-keys`, and `DELETE /api/settings/ali-keys/{ali_id}` send it as `X-Account-Epoch`; they never substitute the current token after invalidation. Settings writes may change the epoch themselves, so their success response is followed by an authoritative connection refresh rather than the account-data response epoch guard. Saving is disabled until an authoritative snapshot is available. The Provider publishes cross-tab notifications before the write and after reconciliation, including on write failure. Storage contains notifications, not authoritative account selection. Configuration writes do not implicitly call connection retry; connection endpoint bodies remain unchanged.

The UI shows `model.configured` as configuration availability only, with actual invocation unverified; the settings step indicator links conceptually to the LLM page in the navigation menu. No client connection, synchronization retry, or model test is performed automatically.

While a readable chat/batch workspace is mounted for a selected seller, it polls `GET /api/conversations/revision` every 10 visible seconds and when the page becomes visible, regardless of key validation. This endpoint is a pure read returning the full sync status with `ready` indicating archive availability. Only one revision request is in flight. Normal observations of the same committed revision do not reload; revision-read, connection, list, or detail failures schedule a recovery reload even if the revision is unchanged. Recovery remains pending until both the list and required active detail finish successfully; without an active detail, only the list is required. A successful revision response never clears the read error, and repeated polls do not schedule additional recovery reads while one is pending. Superseded read acknowledgements are ignored. Background reloads preserve displayed content. The poll uses the workspace's scoped backend, so an old account's response cannot continue against a new account.

Chat, batch, connection and status pages submit manual synchronization through `requestSync`, with independent busy state and captured epoch checks. It does not call account `mutate`, increment generation, broadcast to other tabs, or accept the submission response as completion. Retry also sends `X-Account-Epoch` and rejects mismatched response epochs. After a successful, current-account submission response, an independent read refresh sequence forces one list/detail reload even at the same revision, making CRM profile changes outside IM synchronization visible. It does not invoke AI. The UI reports submission and observes eventual committed data through polling; a later committed revision can trigger another read.

Automatic backup and migration remain backend responsibilities. The frontend displays returned errors and offers configuration correction plus explicit retry. There is no additional migration endpoint or approval flow.

The integrated backend's `account_scope.py`, `connection.py`, and settings/status/self routes have been reviewed against the frontend: envelope, opaque string epoch, Unix-second success timestamp, canonical directory, connection bodies and snapshot fields agree.

The frontend uses `capabilities.read_chat` as the authority, allowing a selected seller's archive to remain readable even when `source.ready` is false or `source.phase` is `syncing`/`error`. Temporary connection failures suspend account requests and writes while retaining the workspace DOM, selection, scroll and drafts. Successful observation of the same account resumes the existing scope; an actual account change or explicit settings invalidation revokes it and remounts. If read capability becomes false, the workspace may unmount; drafts restore using directory, seller and conversation, without epoch in the storage key. Quiet detail refresh merges translations only for identical message IDs and original text and retains analysis, including results completed while the read was in flight. It does not invoke AI. Per-request counters reject superseded list/detail results.

Draft edits are also retained in a module-level store scoped by directory, seller and conversation. A failed localStorage write (including clearing a draft) remains dirty and takes precedence over stale storage values and notifications. Workspace/account changes and failed Provider polls do not clear that store. Loading the draft or successfully refreshing connection state retries pending writes. The fallback survives workspace unmounts within the current browser tab, but cannot survive a full browser refresh or tab close until storage succeeds; the UI explains that limit. React regression tests cover quota failure, background failure/recovery at unchanged revision, committed-version refresh, source progress without reload, account switching, manual sync without remount, AI result merging, stale storage notifications, and eventual persistence.
