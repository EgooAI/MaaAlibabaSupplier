# 统一图片存储实施计划

状态：已实现，已完成隔离回归，真实环境验收待完成。2026-11-17 已确认部署、归档、保留策略及 SDK 泛化边界。存量运行环境尚未迁移或重启。

## 1. 目标与已确认选择

统一两种图片来源的存储与读取：网页上传的待发送图片，以及客户端消息中从阿里平台取回的图片。

用户已确认：

- 由现有后端提供内置本地图床，沿用应用登录和账号作用域。
- 新消息在 CRM 提交后自动归档图片。历史图片首次查看时补存。
- 消息和发送任务引用的图片随记录长期保留。临时上传和无引用对象按期限清理。
- CRM SDK 获得可独立复用的通用资源存储与引用能力，图片业务通过宿主适配接入。

成功标准：相同文件在本机只存一份；已归档消息图片在平台失效或后端重启后仍可显示；两条链路共用同一对象存储；账号切换、图片去重和迁移不改变现有发送身份与核验语义；通用资源能力能够脱离宿主应用独立使用。

| 环节 | 当前实现 | 计划调整 |
| --- | --- | --- |

| 消息图片 | `conversations.py:get_message_image` 每次经 `image_fetch.py` 从平台获取 | 先读本地归档，缺失时下载并持久化 |

### 2.1 SDK 与宿主职责

SDK 使用 SQLModel 模型、`core/` Manager 和共享 SQLite engine。本轮新增通用资源存储，宿主经 `shared/crm/sdk.py` 接入。

| CRM SDK 的通用能力 | 宿主应用的图片业务 |
| --- | --- |
| 具名文件摘要、不可变二进制资源、文件完整性与物理去重 | 上传 PNG 标准化、EXIF 方向、图片格式及体积/像素预算 |
| 本地文件发布、读取、元数据、跨进程一致性 | 阿里平台 URL 解析、签名跳转、网络白名单及重试 |
| 带命名空间的通用资源引用、引用查询与解除 | 卖家、数据目录、会话、Outbox、账号 epoch 和访问授权 |
| 临时引用到期、无引用资源清理的底层操作 | 24 小时草稿期限、长期归档策略、清理调度与备份编排 |
| 可加入调用方事务的资源登记与引用变更 | CRM 同步待办、新旧消息基线、发送核验及 UI 状态 |

SDK 存储任意二进制资源，核心模型使用 `Resource`、`ResourceReference`、`resource_id` 命名。图片是本项目首个消费者，文档等文件可以复用相同接口。首版实现本地存储，避免为了泛化引入暂未使用的远程存储插件体系。

SDK 不导入宿主模块，也不读取 `MAA_*` 配置、调用 GUI、发起平台请求或启动宿主后台任务。文件根目录和通用保留参数由调用方传入，独立使用时可按数据库路径推导默认资源目录。图像解码依赖保留在宿主。

### 2.2 通用接口与事务契约

已新增 `models/resource.py`、`models/resource_reference.py`、`core/resource.py`。本地文件操作与引用事务集中在 `ResourceManager`，避免只有一个使用者的存储抽象：

- `put` 接收字节或二进制流，由 SDK 计算真实文件摘要并返回资源描述。描述可先保持临时保留状态。
- `get` / `open` 查询资源描述或读取文件，文件缺失、损坏和已清理有明确结果。
- `link` / `unlink` 建立或解除指定所有者的引用，`list_references` 查询引用。引用支持明确到期时间，不隐含业务期限。
- `collect_unreferenced` 接收时间和宽限策略，按实际有效引用重新检查后清理，不自行启动定时线程。

引用使用不透明的 `namespace`、`owner_type`、`owner_id`、`slot` 作为唯一业务键。SDK 验证键与引用完整性，不解析其中的卖家或目录，也不按 `owner_type` 字符串猜测和删除业务表。调用方必须在删除业务所有者的同一事务中解除引用。

资源元数据登记、引用建立/替换/解除支持调用方提供同库 SQLModel Session、SQLAlchemy Connection 或 sqlite3 Connection，由调用方决定提交或回滚。SDK 对这些入口使用同一底层 SQLite 连接，写操作获取数据库级写锁。独立调用时 Manager 管理事务。现有 `BaseManager` 的 CRUD 大多自行提交，资源多表操作采用专门实现，不重构其他 Manager。

宿主附件、Outbox 写路径继续使用原生 `sqlite3`，通过 `transaction=conn` 将资源引用加入同一事务。测试在 Outbox 审计写入失败时验证任务和引用期限同时回滚。

通用引用用于资源生命周期与查找，不替代宿主鉴权。直接调用 SDK 的进程属于可信调用方，HTTP 层仍需检查当前业务归属。

## 3. 具名哈希与身份

采用 `算法名:摘要` 格式，以下字段有不同的含义：

| 字段 | 示例格式 | 摘要对象与用途 |
| --- | --- | --- |
| `resource_id` | `sha256:<64位小写十六进制>` | SDK 对实际持久化文件完整字节计算的不可变资源主键 |
| `file_md5` | `md5:<32位小写十六进制>` | 同一份实际文件的 MD5，作为辅助索引和核验材料 |
| `platform_md5` | `md5:<32位小写十六进制>` | 客户端消息报告的 MD5，保存在消息来源记录中 |
| `pixel_id` | `rgba-v1-sha256:<64位小写十六进制>` | 宽高和完整 RGBA 像素的摘要，用于静态图片精确核验 |

建议用 SHA-256 作为唯一存储主键。MD5 保留具名形式，但不承担单独确定对象的职责。已有实测说明，消息里的 MD5/字节数可能对应发送原文件，而下载结果已经重新编码，不能把下载文件直接写到 `platform_md5` 对应的位置。

`rgba-v1` 沿用现有摘要算法：小端无符号 32 位宽、高，再接 RGBA 像素字节。摘要算法或解码规则发生变化时使用新版本名，不能重新解释旧摘要。

文件 SHA-256/MD5 属于 SDK 的通用字节摘要。`pixel_id`、宽高由宿主计算，可作为资源的图像扩展元数据保存，SDK 不解释或计算像素身份。`platform_md5`、平台 URL、上传原件摘要和标准化规则仍保存在宿主来源/附件记录中。

去重规则：

1. 完整文件 SHA-256 相同才复用同一物理对象。复用前校验长度及现存文件完整性。
2. 相同像素、不同编码的文件保留不同对象。可记录相同 `pixel_id`，不据此覆盖字节或合并发送任务。
3. 附件 ID 仍标识一次上传草稿。Outbox ID 和幂等键仍标识一次发送意图。重新选择同一文件可产生新附件 ID，但指向同一 `resource_id`。
4. 不提供仅凭平台 MD5 就给某账号建立图片引用的接口。跨账号允许物理去重，读取权限仍由各自的业务引用决定。
5. 网页上传的原文件摘要、标准化版本属于附件元数据。同一标准化 PNG 可以来自不同原文件，不能把这些字段放成对象的唯一属性。

## 4. 落盘与数据结构

### 4.1 存储目录

通用资源对象放在 CRM 数据库旁，目录由数据库文件名派生。默认布局如下：

```text
backend/data/
  crm.sqlite
  crm.sqlite.resources/
    objects/sha256/ab/cd/<完整64位摘要>
    staging/<随机临时文件名>
```

宿主解析 `MAA_CRM_DB_PATH` 后传给 SDK，默认资源目录为完整数据库文件名追加 `.resources`，避免同名不同扩展名数据库共用目录。SDK 只接收普通路径。接口中的冒号只用于逻辑标识，不进入 Windows 文件名。文件 MIME 类型保存到元数据，不依赖扩展名推断。

### 4.2 数据表与所有权

| 所属 | 表/模型 | 核心字段与职责 |
| --- | --- | --- |
| SDK | 新增 `resource` / `Resource` | `resource_id`、文件摘要、字节数、MIME、扩展元数据、ready/collected 状态、创建时间及临时保留时间。读取时检测缺失和损坏并返回 `ResourceUnavailable`，文件位置由 ID 推导 |
| SDK | 新增 `resource_reference` / `ResourceReference` | 引用 ID、命名空间、所有者类型/ID、槽位、`resource_id`、可空到期时间。上述业务键唯一，资源 ID 使用外键约束 |
| 宿主 | 改造 `app_image_attachment` | 保留附件 ID、卖家、数据目录、会话、原文件摘要、标准化版本和过期信息，增加 `resource_ref_id`。已有 Outbox 继续引用附件 ID |
| 宿主 | 新增 `app_message_image` | 卖家、数据目录、会话、消息 external ID、来源版本指纹、平台 URL 与摘要、`resource_ref_id`、归档状态、重试次数和下次重试时间 |
| 宿主 | 新增 `app_image_archive_scope` | 每个卖家/数据目录的图片归档基线，用于区分首次历史导入与后续新增消息 |

通用引用是资源绑定关系的唯一事实来源。宿主业务表通过 `resource_ref_id` 关联它，不再维护另一份独立可改的对象映射。引用期限的修改与业务状态变更同事务完成，保留策略由宿主传入。

消息来源指纹覆盖与取图相关的原始字段，用于条件更新。后台任务开始时冻结来源快照，结束时只能更新相同指纹的记录。平台字段和本地实际文件字段分别保存，不能用下载后的尺寸或摘要覆盖平台原始声明。

现有 SDK 消息主表不保存完整的同 ID 跨目录正文版本。新的图片来源记录按卖家、目录和消息保存自己的来源快照，读取历史图片不再依赖可能被另一目录同步覆盖的当前消息正文。

SDK 按有效 `ResourceReference` 查询资源是否仍在使用，不读取宿主表、不维护容易漂移的引用计数器。宿主在建立 Outbox 任务的同一事务中将附件临时引用转为长期引用。Outbox 任务仍在时，其附件引用持续有效，包括失败、取消和仅填入任务。

临时引用过期后可保留引用描述与资源描述作为墓碑，实际文件可清理。读取必须检查引用是否有效及资源是否可用，不能把墓碑当作可读文件。重新上传同一原附件时沿用原身份和摘要校验，通过后恢复资源与引用。

### 4.3 文件与数据库的一致性

1. 接收或下载到本目录的临时文件，完成长度、格式和摘要校验，刷新文件数据。
2. 网络传输、图片解码和摘要计算均在数据库写事务外完成。
3. 使用短写事务协调对象发布、业务引用建立和清理。文件在同卷原子发布后，再提交 SDK 资源元数据、通用引用及宿主业务记录。相同 ID 已存在时核验后复用，禁止覆盖不同内容。
4. 成功回执必须晚于文件发布和数据库提交。未完成的文件不对外标为可用。
5. 进程中断遗留的临时文件、已发布但未登记的孤儿文件由后续扫描处理，设置 24 小时宽限期。清理与新引用建立必须互斥，不能在检查无引用后直接无保护地删除。
6. 已有引用的文件缺失或损坏时，明确报告并进入恢复路径，不能返回空图片。按哈希读取的接口不能在同一个 ID 下返回另一份重新编码文件。

文件发布、读取和清理需要覆盖 Web 后端与独立 Agent 的跨进程访问。不能仅靠单进程 Python 锁保证一致性。Windows 文件占用导致清理失败时保留待清理状态，后续重试。

## 5. 两条图片链路

### 5.1 网页上传与发送

```text
选择或粘贴 → 原文件校验 → 标准化 PNG → 写入对象存储
          → 原附件 ID 通过通用引用绑定 resource_id → 预览 / Outbox / 客户端粘贴
```

- 沿用静态 PNG/JPEG/WebP、原文件与发送 PNG 各 10,000,000 字节、最长边 8192、总像素 2400 万的规则。
- 图床保存标准化后的发送 PNG。原文件保留摘要，不另外保存一份上传原件。
- 同附件 ID 重试须校验原文件摘要、归属和固定的标准化结果。哈希去重不能绕过这些校验。
- 上传回执新增 `resource_id`，现有 `id`、宽高、字节数和摘要字段继续保留。
- IndexedDB 草稿、`image:{attachment_id}:{action}` 幂等键、迟到回执隔离继续沿用。
- `PasteChatImage` 通过附件作用域解析对象，并在输入前检查文件完整性。Outbox 的 `may_have_sent` 屏障和单次 GUI 执行规则保持现有语义。

### 5.2 客户端消息图片

```text
消息同步事务：保存消息 + 图片来源快照 + 归档待办
事务提交 → 唤醒图片归档服务 → 下载 → 写入统一对象存储 → 建立消息引用
网页读取 → 优先本地对象；历史未归档则加入同一下载流程
```

新消息归档不依赖网页打开。同步完成只表示 CRM 消息已经提交，图片归档有独立状态；下载失败不回滚消息、不阻止后续聊天同步，也不提前报告图片已保存。

“新消息”按本地首次发现定义，不按平台消息时间判断：

- 每个卖家/目录首次启用时，第一次成功同步建立历史基线，仅登记已有图片来源，不自动下载全部历史。
- 后续首次发现的消息进入自动归档，包括迟到或补录消息。
- 已归档消息的来源发生变化时重新登记对应版本的工作，保留原引用直至新版本完成，避免下载失败先丢失旧图。
- 历史图片首次进入网页可见区时加入归档。已有本地副本直接读取，平台失效不影响已归档副本。

下载保留平台返回的原始编码，不套用发送图片的 PNG 转换。读取侧沿用现有 PNG/JPEG/GIF/WebP 和 20 MiB 下载预算，动画原样归档。静态图满足当前核验解码预算时才计算 `pixel_id`，否则可存文件而不参与精确像素核验。读取预算与发送预算分别定义，不因为统一存储而收紧历史消息的显示范围。

### 5.3 发送核验复用

`ImageVerifier` 先复用本地对象与像素摘要，缺失时使用同一下载入口。仅在源库发现、尚未提交到 CRM 的候选图片以 `image-source` 临时引用保存 24 小时，引用键覆盖作用域、消息 ID、URL、平台摘要、尺寸、方向和时间。这类引用不具备网页读取资格。CRM 提交后可复用同一副本并建立正式消息引用，避免再次下载。

保留现有核验条件：来源、账号、联系人、方向、时间、发送前基线、候选唯一性及竞争任务检查，通过后才判断 MD5/体积或精确像素。文件去重成功不代表发送成功。

被唯一匹配且已提交到 CRM 的出站消息，可以在证据充分时直接引用已有发送 PNG。引用需记录来自哪个任务及何种证据。平台 MD5 和大小均与该 PNG 一致，或已经取得精确像素证据时才允许复用，不能只凭尺寸或模糊相似度关联。

## 6. 后台下载与账号上下文

归档服务复用 `background.py` 的 schedule 和受管 pool。持久化待办以数据库为准，提交后的唤醒只负责降低延迟。即使在 CRM 提交后、唤醒前进程退出，重启仍能找到待办。

- 后台归档并发为 2，继续遵守 `image_fetch.py` 的总并发上限 4。网页按需下载不排入后台队列，相同来源的正在执行下载通过 Future 合并。
- 相同账号作用域、消息及来源版本的后台归档、网页请求和发送核验合并同一进行中下载，避免重复拉取。合并的结果仍须分别校验各调用者的业务权限。
- 队列记录使用 `remote`、`pending`、`fetching`、`ready`、`retry_wait`、`unavailable` 等明确状态。进程重启后失去执行者的下载可重新尝试，不涉及 GUI 重发。
- 网络故障退避重试。平台确认失效后记录不可用，来源更新时可重新尝试。仅空响应先按可重试故障处理，避免签名短暂失效被永久标为删除。
- 网络请求不持账号锁、CRM 写锁、Outbox 锁或 IM 源读取锁。沿用现有 HTTPS 主机白名单、逐跳检查、超时和字节预算。
- 工作项显式捕获卖家、目录、数据库路径、来源指纹和 URL，不在续接中读取新账号凭据。切换账号后不再调度旧工作区新任务，已开始的下载只允许条件提交到原工作区，不更新新工作区页面和状态。切回后恢复待办。
- 下载文件不代表完成。文件发布、数据库映射提交和调用者仍有效分别检查。
- 下载领取 120 秒租约，完成和失败回包必须匹配当前租约，过期执行者不能终结新任务。启动时恢复未完成下载，待办仍在数据库中。
- 按需归档及核验下载也占用后台运行时的工作准入，更新安装期间不启动新下载，进行中的归档阻止安装。
- 归档进度按当前工作区汇总已保存、待下载、重试和失效数量，避免把“消息已同步”显示成“图片已完整归档”。

## 7. 统一读取接口与前端

已增加：

```text
GET /api/images/{resource_id}
```

该宿主接口只返回已存在且有授权业务引用的图片对象，不接受任意外部 URL，也不因用户提交一个哈希就替其建立引用。请求仍带 Bearer token 和 `X-Account-Epoch`，校验当前卖家/数据目录至少存在一个有效附件或消息引用，再经 SDK 读取文件。SDK 提供 Python 资源 API，不包含这个 HTTP 路由及其账号鉴权。

现有两条业务入口继续保留并委托统一服务：

- `/api/conversations/{sid}/image-attachments/{id}/image`
- `/api/conversations/{sid}/messages/{external_mid}/image`

业务入口继续检查会话与消息归属。消息尚未归档时由原消息图片接口触发下载，已有 `resource_id` 时可走统一读取接口。新 `/api/images` 前缀必须同时接入后端和前端的账号作用域识别，保持账号票据传递与响应校验。

前端仍经认证 fetch 取得 Blob 后展示，不把图床目录直接挂为静态路径。首版保留现有 `no-store` HTTP 策略，缓存收益来自后端磁盘。对象 URL 的创建、释放及旧账号回包隔离收敛到共享加载逻辑，两类图片保留各自的业务占位和错误提示。

## 8. 保留、清理与备份

| 对象情况 | 计划保留规则 |
| --- | --- |
| 消息已引用 | 随该消息归档长期保留 |
| 发送或仅填入任务已引用附件 | 随任务长期保留，失败或取消不会自动释放 |
| 上传草稿未形成任务 | 附件临时引用 24 小时后过期，保留原 ID、摘要和归属 |
| 临时引用过期后无其他引用 | 后续清理周期可删除图片内容 |
| 最后一个正式引用被显式移除 | 设置 24 小时宽限期，再检查全部引用后删除 |
| 临时文件或未登记孤儿文件 | 至少保留 24 小时，排除进行中的写入后清理 |

建议由宿主受管定时任务每小时调用 SDK 清理操作，不再依赖有人上传才清理。宿主明确传入期限和宽限策略，SDK 检查全部有效引用后执行删除，不能仅因某个附件过期就删除仍被其他消息、任务或账号使用的文件。

当前没有业务记录删除流程，计划不新增批量删除页面。存量消息及任务引用默认持续存在。磁盘不足时上传明确失败、归档进入可重试状态，不自动淘汰长期保留图片。

备份从单个 CRM 数据库扩展为“CRM 数据库一致快照 + 对应图片目录”。首版完整备份可暂停写入和清理后同时复制两者；只备份 `crm.sqlite` 不再包含全部图片。备份与恢复验收须核对引用文件存在且摘要一致。安装和升级继续保留运行数据目录。

## 9. 存量迁移

1. SDK 增量建立通用资源及引用表，宿主为 `app_image_attachment` 添加可空 `resource_ref_id`，不改变原附件和 Outbox 身份。SDK 迁移不认识宿主旧表，BLOB 搬迁由宿主执行。
2. 分批迁移仍有 BLOB 的附件。通过 SDK 对现有标准化 PNG 字节计算 ID、发布文件并回读校验，不重新编码。成功后在同一事务登记通用引用和宿主关联，迁移可中断续跑。
3. 已过期附件保留原墓碑信息，不制造不存在的文件。已有 Outbox 的正文、摘要、幂等键、`may_have_sent` 和证据不重写。
4. 过渡期附件优先读取对象，尚未迁移时保留 BLOB 读取路径。新对象与引用创建必须经统一服务。
5. 验证所有有效附件可读、相关任务恢复不重发后，再执行单独的数据清理步骤释放旧 BLOB，不直接删表。SQLite 是否压缩另行处理，避免升级过程长时间锁库。
6. 消息图片按工作区建立来源基线，不在升级时自动全量下载历史。首次查看历史消息时按当前作用域导入映射，来源归属不明确时不跨目录借用链接。
7. 保留旧 BLOB 不等于旧版程序可以读取新版新增附件。若需降级，先依据新引用回填所需 BLOB，并验证升级后的数据完整，再切回旧版。

## 10. 实施顺序与验收

### 第一阶段：SDK 通用资源能力与附件迁移

先在独立 SDK 实现具名 ID 校验、文件原子发布、资源模型、通用引用及外部事务接入，并提供不依赖宿主的使用示例。随后由宿主接入附件引用和可恢复迁移，接通上传预览及 `PasteChatImage` 的对象读取。

验收：SDK 可独立存取图片与普通文档字节、绑定不同类型所有者并按引用清理；外部事务回滚时引用同样回滚；同字节多次上传只产生一个对象，但附件和发送任务仍独立；中断不能返回未持久化的成功回执；已有 Outbox 保持原身份且可读取原图。

### 第二阶段：消息图片本地优先

实现按作用域的消息来源映射、首次查看归档及统一读取接口，复用已有 HTTP 下载边界。

验收：首次下载成功后，断开平台访问并重启后端仍可显示；重新编码图片的存储 ID 按实际文件计算；不同账号不能仅凭哈希读取对方图片。

### 第三阶段：自动归档与核验复用

把来源与待办写入消息提交事务，接入受管后台运行时、首次基线、并发合并、退避和归档状态。发送核验复用对象和摘要。

验收：新消息无需网页打开即可保存；历史基线不触发全量下载；提交后进程中断不丢待办；账号切换不会写错工作区；同像素不同编码仍参与发送歧义检查。

### 第四阶段：清理、备份与前端收敛

接入按引用清理、备份恢复验证，合并前端重复的 Blob 加载逻辑，清理迁移过渡路径并更新文档。

需要重点验证的回归：

- 临时上传过期时，共享对象的消息/任务引用仍可读取。
- 清理与新增引用、同哈希并发写入、跨进程读取之间没有删除竞态。
- 来源版本变化后的迟到下载不能覆盖新映射，平台空响应与真正失效分开处理。
- GIF 等读取侧支持的图片不会被发送侧规范化或像素预算误拒绝归档。
- 文件丢失、损坏、磁盘写失败及迁移中断不会变成空图、错误成功或 GUI 重发。
- SDK 测试使用通用租户和所有者数据，在宿主模块不可导入时仍能完成存取、引用、重启读取和回收。SDK 不依赖 Pillow、FastAPI、MaaFW 或宿主运行时。
- 独立 SDK 测试与宿主集成测试分别覆盖事务和清理竞态，尤其是消息/Outbox 写入失败时不得遗留有效引用或提前报告成功。
- 后端临时数据库测试、前端交互测试、类型检查和 lint 通过；真实环境验证归档后离线展示、重启恢复及一张图片发送全过程。

涉及 SDK 修改时，从仓库根使用便携 Python 执行相关宿主与 SDK 测试，显式传入 `-c pytest.ini`。另外运行 `tools/verify_crm_sdk_standalone.py`，验证 SDK 拷贝到独立环境且禁止导入宿主后仍可工作。SDK 是独立 Git 子模块，实施时分别检查主仓库与子模块改动。

## 11. 维护命令

所有操作应指向明确数据库。以下命令为使用说明，本轮没有对运行数据执行它们。

```powershell
# 迁移旧 BLOB，默认保留旧字节。程序后台也会分批执行该步骤。
& '.portable/python/python.exe' -X utf8 tools/maintain_image_resources.py migrate --database backend/data/crm.sqlite

# 备份数据库及所有 ready 资源。目标目录必须尚不存在。
& '.portable/python/python.exe' -X utf8 tools/maintain_image_resources.py backup --database backend/data/crm.sqlite backup-images
& '.portable/python/python.exe' -X utf8 tools/maintain_image_resources.py verify-backup backup-images

# 迁移并回读校验成功后，显式释放原 BLOB。
& '.portable/python/python.exe' -X utf8 tools/maintain_image_resources.py migrate --database backend/data/crm.sqlite --release-legacy
```

备份期间持 SQLite 写锁阻止业务写入和清理，经独立只读连接创建数据库快照，逐文件核验并复制。完成后才写入 `resources-backup.json`，无完成标记的目录不算有效备份。恢复时停止程序，成对恢复数据库及 `.resources` 目录，再运行备份核验。

生效需要构建前端、更新后端并重启、刷新网页。自动迁移保持原 BLOB，只有显式维护命令释放它们。尚需真实客户端及浏览器实际验收。
