# 系统状态与后台执行观察

`GET /api/status` 是系统状态页的聚合入口。页面展示后台任务与连接诊断，观察请求不启动同步、扫描、模型调用、更新检查或 GUI 动作。手动诊断仍通过原有 POST 接口提交。

`POST /api/status/test-tasks` 与节点诊断一样要求 `X-Account-Epoch`，使测试任务进入提交账号的近期列表。状态 GET 不持 GUI 执行锁；前端还会核对响应中的账号 epoch，拒绝展示其他页面切换账号后产生的不匹配快照。

## 数据范围

已有 `source`、`workers`、`queues`、`pools`、`modules` 和 `lastDiagnostic` 字段继续提供源库、常驻服务、队列、卡片缓存与连接证据。新增 `background` 提供以下信息：

| 字段 | 范围与含义 |
| --- | --- |
| `runtime` | 当前 API 进程受管资源及有限的已结束历史。包含执行状态、当前并发、排队数量、完成与异常计数、最近执行时间及下一轮计划时间 |
| `queueTasks` | 当前账号 epoch 下 GUI 和翻译队列的任务，每个队列最多 100 条，运行中优先，其次排队和近期结束记录。排除已过保留期的记录，先过滤 Outbox 再截断。Outbox 的结果以持久化工作流为准 |
| `queueCounts` | 当前账号 epoch 下各队列保留期内的全量状态计数，不受列表 100 条上限影响。主状态与排队、执行、失败数量使用这些计数 |
| `experiments` | 当前卖家与数据目录的实验运行，活动任务优先，最多 50 条。包含各变体状态及 `cancelRequested` |
| `outbox` | 当前卖家与数据目录的持久化状态计数，以及最多 20 条近期任务元数据。查询不初始化或迁移表，不返回消息正文、收件人、截图或核查证据内容 |
| `update` | 已存在更新器的已发布状态、下载进度与错误。观察不创建更新器，也不探测或改变安装辅助进程 |
| `errors` | 单个数据源的观察失败，例如 `outbox` 数据库暂不可读或 `update` 状态锁忙。其余来源仍可展示，失败来源不能解释为空队列或零任务 |

运行时和队列执行器统计属于整个进程，可能包含切换账号前尚未结束的工作。业务任务列表按当前工作区过滤，实验的原始 worker 不在进程资源列表中重复暴露。卡片扫描和 Outbox 核查的账号相关计数只有上下文匹配时才显示。`observedAt` 与各来源时间表示采样时间，不承诺整个响应来自同一个跨模块事务。

## 状态语义

- `starting`、`waiting`、`running`、`blocked`、`stopping` 分别表示启动中、等待、执行中、准入条件未满足、正在停止。下一轮计划时间只适用于定时调度，手动触发服务可以没有该时间。
- `stopped` 表示已退出的 worker，正常停止不等于失败。`failed` 表示运行时捕获的异常，错误仅暴露异常类型。
- `completed` 及运行时完成计数表示调用结束。GUI 或翻译业务返回失败时，即使其宿主 worker 正常运行，任务结果仍以队列快照为准。循环完成也不表示源库新鲜或 CRM 已提交。
- 实验发出取消请求后，仍可能等待在途模型调用结束。只有运行状态进入终态，才显示已取消或已结束。
- Outbox 的 `awaiting_confirmation` 需要在聊天工作台确认截图。`verifying` 表示核查中，`unknown` 表示结果不确定，`observed` 仅表示本地发现匹配消息，`filled` 仅表示已填入。状态页不据此自动重发或宣称平台送达。
- 更新器的已下载或已就绪状态不表示已安装。安装仍从设置页手动确认。

## 页面生命周期

可见页面按两秒间隔串行读取，隐藏后暂停，恢复可见或重新获得焦点时立即读取。请求失败保留当前账号的最后快照并提示过期，用户可手动刷新。

切换账号立即清空旧快照，允许新账号发起读取。旧请求、旧动作及卸载后的异步续接不能发布结果、弹出通知或使用新账号继续旧操作。动作提交成功仅表示已接受，需要后续状态确认执行结果。旧后端缺少 `background` 时，页面明确显示观察数据尚未提供。
